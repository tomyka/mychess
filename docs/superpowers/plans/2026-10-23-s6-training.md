# S6 Training Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A player learns new moves (a line with arrows, then blind, R-144)
and reviews Due Moves by FSRS (jump-then-chain, lapse replay, hint, sessions
of 20 with "continue"), from home over every repertoire or from one
repertoire's page. They can mark moves "I know this" and undo it, set their
two limits, and keep drilling through a dropped connection: results queue
locally and sync later.

**Architecture:**
- **Chess** (`packages/chess/src/training/`): pure and shared by server and
  browser. Adds the stored-review schema, the line so far to a move, the
  learn plan, the two drill state machines, "two answers", and the keys
  "Learn again" may return.
- **Domain** (`packages/domain/src/training.ts`, `calendar.ts`,
  `rate-limit.ts`): training settings, the result-batch schema, whether and
  how a result applies (`acceptResult`, `canRecord`), the learn order across
  repertoires (R-145), the player's day, and the results rate limit.
- **Database** (`packages/db/src/training-schema.ts`, `src/training/`):
  `reviews`, `review_results`, two settings columns on `accounts`. It loads a
  training snapshot, records result batches idempotently, and handles "I know
  this", "Learn again" and the learned set. The learned set replaces S5's
  `NOTHING_LEARNED`.
- **Web** (`apps/web`): the server sends one serialisable snapshot (ordered
  repertoires, held reviews, learned today, settings). The browser builds the
  queue and the plan with the same chess functions, judges each answer at
  once, grades its own copy for "continue", and queues each result in
  localStorage for `POST /api/training/results`. The server grades again and
  its grade is the one that counts (spec decision 1).

**Tech Stack:** ts-fsrs 5.4.2, Drizzle 0.45.3 on Postgres 18, Next.js 16.3
App Router (server components, route handlers, server actions), next-intl 4,
zod 4, vitest 4 (Testcontainers for db), fast-check, Playwright 1.64,
chessground (the existing `apps/web/src/app/board`).

## Decisions taken while planning

None of these is a product rule. Possible product rules are listed under
"Spec gaps for the owner" at the end.

1. **The browser runs the same pure functions as the server.** The snapshot
   carries the graphs and reviews. The browser builds the queue and learn
   plan, grades a local copy (so "continue" and the done summary work while
   offline), and queues every result. The server ignores the browser's
   schedule and grades from its own row.
2. **One review row per (player, move key).** The FSRS card is stored as
   columns (`due` is indexed). `lapse_times` holds the R-56 lapse history.
   `skipped_at` is set by "I know this", `learned_at` by a learn pass.
   Exactly one of the two is set (CHECK).
3. **Results apply in arrival order, judged by time.** A graded result whose
   clamped `answeredAt` is earlier than the row's `last_review` is `stale`:
   logged, not applied. FSRS cannot replay out of order, and a later answer
   already holds the newer schedule.
4. **`review_results.result_id` is the primary key.** An insert with
   `onConflictDoNothing` that returns no row means `duplicate`, and nothing
   else is done for it.
5. **Each batch runs in one transaction.** It locks the player's touched
   review rows `FOR UPDATE` in key order (no deadlock between two tabs), then
   applies the results in `answeredAt` order.
6. **Held is checked per result** with `canRecord`: the result's repertoire
   must be one the player trains now and must hold the key. A paused
   repertoire refuses `learned` (`training.paused`) but accepts review
   outcomes. Pausing stops new items, and an answer already given is kept.
7. **The learn order (R-145) is a domain sort** over `TrainingEntry` values
   (kind, deadline, created order). `trainingRepertoires` keeps its contract.
   A new `trainingEntries` returns entries with name, kind and deadline,
   sorted by `learnOrder`.
8. **Settings live on `accounts`** (`session_size`, `new_per_day`), read and
   written by their own repository functions. The `Account` type does not
   change.
9. **The training page is `/treniruote`** with `?mode=review|learn` and an
   optional `&r=<repertoireId>`. i18n-content may rename the slug in Task
   D1. Only `ROUTES.training` and `trainingPath` name it.
10. **The offline queue** is one localStorage key per account,
    `mychess.results.<accountId>`. Its contents are parsed with the domain
    batch schema on read, and an unparsable value is discarded. It is
    flushed in batches of at most 50, on each new result, on `online`, on
    `pageshow`, and every 30 s while non-empty.

/**
 * The line so far to a move (R-143): the chapter walk's path from the
 * chapter's root to the move, in the first chapter that holds it. After a
 * transposition that is the path the walk took first (as chapterPlies).
 */
import {
  moveKey,
  type RepertoireGraph,
  type RepertoireMove,
} from '../repertoire/graph';
import { chapterWalks, type WalkedMove } from '../repertoire/walk';

export interface LineTo {
  readonly chapterId: string;
  readonly rootKey: string;
  /** From the root; the move asked about is last. */
  readonly moves: readonly RepertoireMove[];
}

interface Frame {
  readonly walked: WalkedMove;
  readonly path: readonly RepertoireMove[];
}

function pathIn(tree: readonly WalkedMove[], key: string): RepertoireMove[] | undefined {
  const stack: Frame[] = tree.map((walked) => ({ walked, path: [] })).reverse();
  for (let top = stack.pop(); top !== undefined; top = stack.pop()) {
    const { move, next } = top.walked;
    const path = [...top.path, move];
    if (moveKey(move.from, move.san) === key) return path;
    for (const child of [...next].reverse()) stack.push({ walked: child, path });
  }
  return undefined;
}

export function lineTo(graph: RepertoireGraph, key: string): LineTo | undefined {
  const walks = chapterWalks(graph);
  for (const chapter of graph.chapters) {
    const moves = pathIn(walks(chapter.id).tree(), key);
    if (moves !== undefined)
      return { chapterId: chapter.id, rootKey: chapter.rootKey, moves };
  }
  return undefined;
}
```

### Task A3: `learnPlan` (chess-dev)

**Files:**
- Create: `packages/chess/src/training/learn-plan.ts`
- Test: `packages/chess/src/training/learn-plan.test.ts`

What it does (R-144, R-145, U1-M1-4):
- It takes the active repertoires in the caller's order (R-145), each chapter
  in order, and each root-to-leaf path of the chapter's walk tree. Each move
  appears once in the tree, so the paths stay linear in size.
- A path is planned when it has a player move that is not learned and not
  already planned. Its steps are tagged:
  - `opponent`: an opponent move;
  - `known`: a player move already learned, or planned earlier in this plan;
  - `new`: a player move to learn now.
- Planning stops when `limit` new moves are planned. The path that reaches
  the limit is cut right after its last `new` step.
- Keys in `learned` are never taught again, so shared positions learned in
  another line come up as `known` (U1-M1-4).

/**
 * The learn pass's lines (R-144, R-145): what to teach next, as whole lines
 * from a chapter's root, so each new move is learned in context. The
 * caller orders the repertoires (domain learnOrder) and gives the allowance
 * left today (R-62, R-146).
 */
import {
  isPlayerMove,
  moveKey,
  type RepertoireGraph,
  type RepertoireMove,
} from '../repertoire/graph';
import { chapterWalks, type WalkedMove } from '../repertoire/walk';
import type { TrainingRepertoire } from './scope';

export type LearnStepKind = 'opponent' | 'known' | 'new';

export interface LearnPlanStep {
  readonly kind: LearnStepKind;
  readonly move: RepertoireMove;
  readonly key: string;
}

export interface LearnLine {
  readonly repertoireId: string;
  readonly chapterId: string;
  readonly rootKey: string;
  readonly steps: readonly LearnPlanStep[];
}

/** Every root-to-leaf path of a walk tree, each move of the tree once per path. */
function treePaths(tree: readonly WalkedMove[]): RepertoireMove[][] {
  const out: RepertoireMove[][] = [];
  const stack = tree.map((w) => ({ w, path: [] as RepertoireMove[] })).reverse();
  for (let top = stack.pop(); top !== undefined; top = stack.pop()) {
    const path = [...top.path, top.w.move];
    if (top.w.next.length === 0) out.push(path);
    for (const child of [...top.w.next].reverse()) stack.push({ w: child, path });
  }
  return out;
}

interface Planner {
  readonly taught: Set<string>;
  left: number;
}

function stepOf(graph: RepertoireGraph, move: RepertoireMove, planner: Planner): LearnPlanStep {
  const key = moveKey(move.from, move.san);
  if (!isPlayerMove(graph, move)) return { kind: 'opponent', move, key };
  if (planner.taught.has(key) || planner.left === 0) return { kind: 'known', move, key };
  planner.taught.add(key);
  planner.left -= 1;
  return { kind: 'new', move, key };
}

/** The path's steps up to its last new move, or none when it has nothing new. */
function planPath(graph: RepertoireGraph, path: readonly RepertoireMove[], planner: Planner): LearnPlanStep[] {
  const steps = path.map((move) => stepOf(graph, move, planner));
  const last = steps.findLastIndex((s) => s.kind === 'new');
  return steps.slice(0, last + 1);
}

function* candidateLines(repertoires: readonly TrainingRepertoire[]) {
  for (const r of repertoires.filter((x) => x.active)) {
    const walks = chapterWalks(r.graph);
    for (const chapter of r.graph.chapters) {
      for (const path of treePaths(walks(chapter.id).tree()))
        yield { r, chapter, path };
    }
  }
}

export function learnPlan(
  repertoires: readonly TrainingRepertoire[],
  learned: ReadonlySet<string>,
  limit: number,
): LearnLine[] {
  const planner: Planner = { taught: new Set(learned), left: limit };
  const plan: LearnLine[] = [];
  for (const { r, chapter, path } of candidateLines(repertoires)) {
    if (planner.left === 0) break;
    const steps = planPath(r.graph, path, planner);
    if (steps.length > 0)
      plan.push({ repertoireId: r.id, chapterId: chapter.id, rootKey: chapter.rootKey, steps });
  }
  return plan;
}
```

How it behaves (R-143, R-59, R-61, R-78):
- The session holds the queue's `reviews` items in order, the repertoires

- `current` is the item asked now. `line` is `lineTo(graph, item.key)` for

- Events:
  - **`answer(san)`:**
    - The right SAN with no outcome yet: the outcome is `pass`, emitted, and
      `phase: 'correct'`.
    - The right SAN when the outcome is already `lapse` or `hint`: no emit,
      `phase: 'correct'`.
    - A wrong SAN with no outcome: `lapse` is emitted and `phase: 'replay'`
      (the arrow is shown, R-59).
    - A wrong SAN in `replay`, or after an outcome: no emit, and the phase
      stays the same.
  - **`hint()`:** with no outcome yet, emits `hint` and sets `hinted: true`
    (the UI highlights the piece on `item.fromKey` that plays `item.san`).
    Otherwise it changes nothing.
  - **`next()`** (only from `phase: 'correct'`). The opponent reply is the
    first child of the answered move's `to` position, in the item's chapter,
    that is followed by a player move whose key is an unanswered item. If
    there is one, that item moves to be next, and its `line` is the current
    line plus the reply plus the move (chained, R-143). Otherwise the next
    unanswered item in order. When none is left, `done`.
- Each item emits exactly one outcome: the first of `hint`, `lapse` or
  `pass` (R-59, "recorded once").

// calendar.ts
const PARTS = (timeZone: string) =>
  new Intl.DateTimeFormat('en-US', {
    timeZone, hourCycle: 'h23', year: 'numeric', month: 'numeric', day: 'numeric',
    hour: 'numeric', minute: 'numeric', second: 'numeric',
  });

/** Minutes `timeZone` is ahead of UTC at `at`. */
function offsetMinutes(at: Date, timeZone: string): number {
  const parts = Object.fromEntries(
    PARTS(timeZone).formatToParts(at).map((p) => [p.type, p.value]),
  );
  const local = Date.UTC(
    Number(parts.year), Number(parts.month) - 1, Number(parts.day),
    Number(parts.hour), Number(parts.minute), Number(parts.second),
  );
  // formatToParts drops milliseconds, so compare against whole seconds.
  const wholeSeconds = at.getTime() - at.getUTCMilliseconds();
  return Math.round((local - wholeSeconds) / 60_000);
}

/** The instant the calendar day of `at` begins in `timeZone` (R-146). */
export function dayStart(at: Date, timeZone: string = HOME_TIME_ZONE): Date {
  const [y, m, d] = new Intl.DateTimeFormat('en-CA', { timeZone, year: 'numeric', month: '2-digit', day: '2-digit' })
    .format(at).split('-').map(Number);
  const midnightUtc = Date.UTC(y ?? 1970, (m ?? 1) - 1, d ?? 1);
  const guess = midnightUtc - offsetMinutes(new Date(midnightUtc), timeZone) * 60_000;
  return new Date(midnightUtc - offsetMinutes(new Date(guess), timeZone) * 60_000);
}

```ts

 * Records a parsed batch for `playerId` (the session account) at `now`, in
 * one transaction (S6 decisions 2-6). Returns one answer per result, in
 * the batch's order.
 */
export function recordResults(db: Executor, playerId: string, batch: readonly TrainingResult[], now: Date): Promise<ResultAnswer[]>;
```

Steps inside the transaction:
1. **Entries.** Get the player's `trainingEntries` (in the same
   transaction). For each result, `facts.repertoire` is the entry with that
   id, mapped to `{ active, holds: playerKeys(graph).includes(moveKey) }`.
   Build a `Set` per entry once; do not call `playerKeys` per result.
2. **Lock.** Lock the touched rows: `select … from reviews where player_id
   = $1 and move_key = any($2) order by move_key for update`.
3. **Order.** Sort the results by clamped `answeredAt`, then by batch index.
4. **Known ids.** One `select result_id from review_results where
   result_id = any($1)` over the batch's ids. Those ids, plus any id seen
   earlier in the same batch, answer `duplicate` and are skipped.
5. **Per new result:**
   1. `canRecord`. A refusal answers `refused`.
   2. `acceptResult(kind, at, stored)`, where `stored` comes from the
      locked rows map and is updated in memory as results apply. A refusal
      answers `refused`; `stale` answers `stale`.
   3. On `apply`:
      - `learned`: `startReview(key, at)`, then insert with `learned_at =
        at`.
      - otherwise: `grade(review, kind, at)`, then update the card columns,
        `lapse_times` and `updated_at = now`.
      - Answer `applied`.
   4. Whatever the answer, insert the log row with `applied = (answer === 'applied')` and
      `onConflictDoNothing({ target: reviewResults.resultId })`. A batch
      racing another batch with the same id is held off by the row locks
      of step 2 only when both touch the same key, and a result id belongs
      to one key, so the conflict clause is only a backstop.
6. **Return** the answers in the original batch order.

and reuse `toReviewState` from B2 for reading.
