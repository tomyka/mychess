# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MyChess (mychess.lt) — a general chess-training platform (openings/repertoires, spaced-repetition drilling, tournaments, FIDE/Lichess/Chess.com integration). **This is not a kids' product** — an early idea that was dropped; don't apply kid-safety/COPPA-style framing to features or copy.

Stack: SvelteKit 2 + Svelte 5 (runes), Supabase (Postgres + Auth, via `@supabase/ssr`), Tailwind 4, deployed on Vercel (`adapter-vercel`, Node 22.x runtime).

## Repo layout

The git repo root is one level **above** this directory (`git rev-parse --show-toplevel`; the path is machine-specific, so don't hardcode it). This directory (`mychess/`) is the actual SvelteKit app — all `npm` commands run from here. Design specs and implementation plans from past features live one level up, at `../docs/superpowers/specs/` and `../docs/superpowers/plans/`, not under this directory's own (mostly stale) `docs/`.

## Commands

Run from this directory (`mychess/`):

- **`npm run setup` — the first thing to run in a fresh worktree or checkout (GitHub issue #192).** A bare `npm install` is not enough on this project's dev machines, and both reasons fail in ways that look like a broken repository rather than a broken environment: `.npmrc` sets `engine-strict=true` against a Node older than some devDependencies want (`EBADENGINE`), and npm's optional-dependency bug (npm/cli#4828) silently drops rolldown's platform-specific native binding, after which vitest and vite die with `Cannot find native binding`. This script installs with the engine override, restores the binding at the version in `package-lock.json` (resolved by matching the lockfile's own `os`/`cpu` entries — nothing is hardcoded), proves rolldown actually loads, and then runs the suite. Add `--no-test` to stop after the binding check.
  - Note the binding repair runs on **every** setup, not just the first: `npm install` drops it again each time, so deleting `node_modules` and reinstalling never fixes it on its own.
  - It distinguishes the two failure kinds deliberately. A failure before the binding loads says *environment problem, not a code problem*. A test failure after it says the opposite — the toolchain is fine and those are real failures. Mislabelling that is exactly what sends someone hunting the wrong bug.
- `scripts/backlog-run-guard.mjs` — **not run by hand.** A hook that hard-caps what one run may spend (GitHub issue #193). Wire it in `.claude/settings.local.json` on each machine (that directory is gitignored, so it does not follow you between them):
  ```json
  "PreCompact":    [{ "matcher": "auto", "hooks": [{ "type": "command", "command": "node mychess/scripts/backlog-run-guard.mjs" }] }],
  "SubagentStart": [{                    "hooks": [{ "type": "command", "command": "node mychess/scripts/backlog-run-guard.mjs" }] }]
  ```
  It refuses a subagent past `BACKLOG_MAX_SUBAGENTS` (default 20), a run past `BACKLOG_MAX_MINUTES` (default 120), and **automatic** compaction — so a session whose context is nearly full stops instead of summarising itself and carrying on. Manual `/compact` is always allowed; `BACKLOG_ALLOW_AUTOCOMPACT=1` permits the automatic kind.
  - The point of a hook rather than a rule in this file: the harness runs it, so it cannot be reasoned past. Caps written as instructions are checked by the agent against itself, and an agent that has lost the thread is exactly the one that will not check.
  - It fails **open** on any internal error, deliberately — a guard that failed closed on its own bug would block every subagent in every session, including ordinary supervised work that never asked for a cap.
  - **It is not a spend cap.** Hooks receive no cost or context-percentage figure, so this counts spawns and minutes, which correlate with spend but are not it. For a real dollar ceiling, launch with `claude --max-budget-usd <n>`.
- `npm run dev` — dev server (Vite)
- `npm run build` / `npm run preview` — production build / preview it locally
- `npm test` / `npm run test:watch` — vitest (unit tests, colocated `*.test.ts` files)
- `npx vitest run path/to/file.test.ts` — run a single test file
- `npm run check` / `npm run check:watch` — `svelte-kit sync` + `svelte-check` (TypeScript + Svelte type checking)
- `npm run lint` — `eslint .` (flat config in `eslint.config.js`, includes `eslint-plugin-svelte` and `eslint-plugin-security`)
- `npm run fide:import` — one-off script (`scripts/import-fide.ts`) to bulk-import FIDE player data
- `npm run eco:generate` — one-off script (`scripts/generate-eco-data.ts`) to regenerate ECO opening data
- `npm run qa:verify-learn -- "<path-to-pgn>"` — standard way to verify a Learn/picker fix end-to-end (GitHub issue #179): uploads the given PGN as a persistent `qa-coach@mychess.lt` fixture, assigns it to `qa-player@mychess.lt`, drills it through the real practice-attempt API, then drives a real browser to `/learn/<id>` and checks the rendered picker — against production by default, or `QA_BASE_URL=http://localhost:4173` for a local build+preview. Prefer this over asking a human to manually reproduce and screenshot a Learn/picker bug.
- `npm run debug:learn-plan -- <repertoireId> <playerId>` — read-only diagnostic (GitHub issues #180, #182) that replicates `/api/repertoires/[id]/learn-units`'s exact `deriveLearnPlan` derivation against live production data, using the real `$lib/mastery/*` pure functions (imported by relative path — see the script's own header comment on why `$lib` aliases don't resolve outside SvelteKit's Vite context). Prints each chapter's current band and its unlearned units, plus every variation's teaching cap and mastered-ply count, so a "why am I being shown this line" report can be root-caused from data instead of guessed at.
- `npx playwright test` — e2e tests (`tests/*.e2e.ts`); builds and previews the app first, runs against Chromium + a Pixel 5 mobile profile

CI (`.github/workflows/ci.yml`) runs `npm test` and `npm run lint` before deploying; `check` is not gated there, so running it locally before pushing is on you.

**`npm run check` and `npm run lint` must both report zero errors before pushing to `main`.** There is no tolerated baseline — a prior one (OAuth callback/connect routes' `string | undefined` env-var typing) was fixed via `requireEnv()` in `src/lib/env.ts`, which narrows a `$env/dynamic/*` value to `string`, throwing a clear error if it's actually missing. Use it for any new required env var read outside `+layout.server.ts`'s existing patterns, rather than reintroducing the same class of error.

Lint has no tolerated baseline either (issue #91): `npm run lint` is gated in CI as of that fix, and `eslint.config.js` now hands the TypeScript sub-parser to `**/*.svelte.ts`/`**/*.svelte.js` as well as `**/*.svelte` — without it, `eslint-plugin-svelte`'s base config points rune modules at `svelte-eslint-parser` alone and every one of them dies on its first type annotation, so they read as "errors" while actually going unlinted. Its ~164 warnings (mostly `@typescript-eslint/no-explicit-any`, deliberate at Supabase/webhook boundaries) are not gated and are not a baseline to clear.

## Database & migrations

- SQL migrations live in `supabase/migrations/*.sql`, numbered sequentially (`0001_...` onward).
- **A working `SUPABASE_SERVICE_ROLE_KEY` is available in `mychess/.env`** (since 2026-08-19) — use it for direct data-level operations against production via the REST API/`supabase-js` (ad-hoc `select`/`delete`/`update`, checking a table's live shape, cleaning up QA/test accounts), bypassing RLS. This does **not** enable schema migrations: PostgREST can't execute DDL. There is still no local Postgres and no linked Supabase CLI / direct DB connection string in this environment, so Claude cannot apply `supabase/migrations/*.sql` directly — write the migration file, then paste its contents for the user to run manually in the Supabase dashboard SQL editor (or trigger the `migrate.yml` GitHub Action if asked). Never assume a migration took effect — if a feature depends on new schema/RLS, ask the user to confirm they ran it before relying on it.
- Migration files can drift from the live schema (has happened at least twice — `repertoires`/`moves` columns, and `coach_notes`). Before writing code against a table whose shape you're unsure of, use the service-role key to check `information_schema.columns` (or `select *`) directly rather than trusting the migration history.
- RLS is used throughout. Remember: a `WITH CHECK` clause cannot reference the pre-update (`OLD`) row — enforcing column immutability on `UPDATE` requires a `BEFORE UPDATE` trigger instead. Also remember Postgres ORs together multiple permissive policies for the same operation — a broad `for all` policy silently defeats a narrower same-operation policy added alongside it; split into single-operation policies instead.
- Supabase's default `anon` grant on new views/tables isn't revoked by granting to `authenticated` — add an explicit `REVOKE ALL ... FROM anon, public` when a view shouldn't be public.
- `.upsert()` without an explicit `onConflict` targets the table's primary key, not other unique constraints — always pass `{ onConflict: '<col1>,<col2>' }` explicitly when upserting against a non-PK unique constraint (e.g. `assigned_repertoires`'s `unique(player_id, repertoire_id)`).

## Architecture

**Route groups gate by role**, enforced in each group's `+layout.server.ts`:
- `src/routes/(player)/` — default player experience. `/` (the landing page) still renders for a signed-out visitor with no account; all seven sub-pages (`badges`, `coaches`, `cosmetics`, `drill`, `practice`, `repertoires`, `time-trial`) require a real account via `requireAccount`. A `role: 'coach'` profile is redirected to `/coach`.
- `src/routes/(coach)/` — requires a real (non-anonymous) session with `profile.role === 'coach'`; everyone else is redirected to `/` or `/login`.
- `src/routes/auth/`, `/login`, `/welcome`, `/join/[token]` — outside both groups (auth flows, onboarding, invite redemption).
- `src/routes/api/` — JSON endpoints (cron-triggered jobs, imports, quest/review progress) rather than page routes.

**Auth model** (`src/hooks.server.ts`, `src/lib/server/auth.ts`):
- `locals.safeGetSession()` is the single source of truth — returns `{ session, user, profile, isSignedOut }`. It does *not* eagerly create a session; public pages render with `user: null`.
- **Anonymous auth is fully retired — don't reintroduce it, and don't add `is_anonymous` handling back.** `/drill` and `/time-trial` used to lazily mint an anonymous Supabase session (`ensureGuestSession`) from their `load` functions, but a SvelteKit `load` runs on every GET, so crawlers and link-preview bots were minting throwaway accounts just by visiting the URL. #88 removed the minting, #90 purged the 3,811 rows it had left (none held any progress; none had ever converted), and the Supabase "Anonymous sign-ins" provider is disabled, so no anonymous session can exist or be created. If a "try without an account" mode is ever wanted, it needs a fresh design — the failure was minting accounts from a `load`, not the idea of guests.
- `isSignedOut` now means exactly "no session". It used to mean "no usable real account" (no user *or* an anonymous one), which is why `src/hooks.server.ts`, `src/routes/(player)/+page.server.ts`, `src/routes/(player)/+layout.server.ts`, `src/routes/(coach)/+layout.server.ts`, `src/lib/server/auth.ts` and `src/lib/components/NavBar.svelte` each carried an explicit `is_anonymous` check. All six are gone now that the provider is off and the rows are purged. `src/lib/auth/client.ts`'s `sendMagicLink` lost its anonymous-conversion branch (and the `getUser` round trip it needed) for the same reason.
- `requireAccount(locals)` is the guard for pages/actions that need a real account — it rejects anonymous sessions too (deliberately, same reasoning as above) and throws a redirect to `/login` otherwise. Because TypeScript can't narrow its return type, call sites use `user!.id` afterward, matching existing sibling files — this is intentional, not a defect to "fix."
- `src/hooks.server.ts` backfills `display_name` from `first_name`/`last_name` for any profile whose name is a placeholder (`isPlaceholderName` in `src/lib/profile.ts`, now true only for an empty name). The literal `"Guest"` used to count as a placeholder as well, via a `GUEST_DISPLAY_NAME` constant, because the guest-auth flow named profiles that; both are gone with #90's purge, so a player who genuinely calls themselves "Guest" keeps that name.

**Code split: pure logic vs. Supabase I/O.** Throughout `src/lib/`, business logic that can be unit-tested without a database lives in a plain module (e.g. `src/lib/pgn-import.ts`, `src/lib/repertoire.ts`, `src/lib/coach-players.ts`, `src/lib/fide/*.ts`, `src/lib/tournaments/*.ts`, `src/lib/badges/*.ts`, `src/lib/quests/*.ts`) with a colocated `*.test.ts`. Anything that actually touches `supabase` lives in `src/lib/server/` (e.g. `src/lib/server/pgn-import.ts`, `src/lib/server/coach-players.ts`) and, following established precedent, is generally *not* unit-tested directly — it's a thin wrapper around the pure logic plus DB calls, exercised through the pure-logic tests and manual/e2e verification instead.

**Key domains under `src/lib/`:**
- `pgn/` — PGN parsing into position graphs (`parser.ts`), consumed by `pgn-import.ts` to build `repertoires`/`positions`/`moves` rows.
- `fide/` — FIDE rating lookup, search, and ranking logic; `download.ts`/`import-job.ts` back the `fide:import` script and the cron-triggered `/api/fide/import` route.
- `tournaments/` — tournament listing/filtering/ranking (`query.ts`) plus a scraper (`scraper.ts`, `scrape-job.ts`) that also runs as a Supabase Edge Function (`supabase/functions/tournaments-scrape/`) and via `/api/tournaments/scrape`.
- `badges/`, `quests/`, `cosmetics.ts` — gamification layer (grants, recalculation, daily quest generation).
- `coach-players.ts` (+ `server/coach-players.ts`) — the many-to-many coach↔player relationship system: request/accept flow, invite-link redemption (`/join/[token]`), and directory browsing (`/coach/students` finding players, `/(player)/coaches` finding coaches). This has its own guard-trigger-based anti-hijack protection at the DB layer (see migrations 0019–0021) — don't bypass it by writing directly instead of through the relationship functions. Directory browsing is backed by two Postgres views, `coach_directory`/`player_directory` (migration 0019), over a dedicated `directory_profiles` table (migration 0067) rather than `profiles` directly: `profiles`' own RLS only allows a user to see their own row or one they have a `coach_players` relationship with, which is exactly what directory browsing needs to see past. `directory_profiles` holds just the 5 already-narrow, non-sensitive columns the views expose (`id`, `first_name`, `last_name`, `display_name`, `avatar_id`), kept in sync from `profiles` via an `after insert or update` trigger (`sync_directory_profile`, `security definer set search_path = public`, matching `update_weekly_leaderboard`'s pattern), with a genuinely open `for select using (true)` RLS policy — safe only because that table can never hold anything more sensitive than those 5 columns. Both views are real `security_invoker = on` views over it (Supabase Security Advisor previously flagged them as SECURITY DEFINER when they queried `profiles` directly with an implicit privilege bypass; a same-table fix isn't possible since RLS is row-scoped, not column-scoped, so any policy broad enough to make `profiles`-backed views work under `security_invoker` would equally let any authenticated user query all 13 columns of `profiles` directly, not just these 5). An earlier version of `player_directory` also excluded guest/anonymous accounts by joining `auth.users.is_anonymous` (migration 0056) — removed in migration 0066 once anonymous auth was fully retired (the join was itself flagged as `auth_users_exposed` by the Security Advisor, and had been a no-op since guest accounts stopped being creatable).
- `repertoire.ts` / `server/pgn-import.ts` — repertoires are position/move graphs built from parsed PGN; a repertoire is *owned* by whoever uploaded it (`repertoires.player_id`) and separately *assigned* to students via `assigned_repertoires` (coach_id, player_id, repertoire_id) — ownership and assignment are deliberately decoupled so a coach can build a personal library and assign the same repertoire to many students.

**Chess platform integrations** (`src/lib/server/{lichess,chesscom,oauth}.ts`, `src/routes/auth/{connect,callback}/*`): OAuth/PKCE flows to link Lichess and Chess.com accounts, plus a custom Google Sign-In flow — all hand-rolled against each provider's token endpoint rather than a generic OAuth library. `oauth.ts` centralizes signed-state handling (`OAUTH_STATE_SECRET`). A separate, purely client-side OAuth interaction — `src/lib/googleDrivePicker.ts` (Google Identity Services token client + Picker API, `drive.file` scope, for importing a PGN directly from Google Drive) — is unrelated to the sign-in flow above and needs its own Google Cloud Console configuration: it depends on `PUBLIC_GOOGLE_CLIENT_ID`'s **Authorized JavaScript origins**, not the sign-in flow's Authorized redirect URIs. Mixing these two up is a common source of `invalid_client`/`no registered origin` errors.

**Client-side chess UI:** `chess.js` for rules/move validation, `chessground` for the interactive board, wrapped by `src/lib/components/ChessBoard.svelte`.

**PWA:** `@vite-pwa/sveltekit` (configured in `vite.config.ts`) generates a service worker with `NetworkFirst` caching for Supabase REST calls; manifest/icons under `static/`.

**Deployment:** pinned to Vercel region `arn1` (Stockholm) in `svelte.config.js`, matching the Supabase project's North EU region — without this, Vercel defaults to `iad1` (US East), forcing every server-side Supabase round trip across the Atlantic for no reason.

**Auth emails:** the magic-link sign-in email uses a branded HTML template at `supabase/templates/magic_link.html`, wired into `supabase/config.toml` for local dev only. As with migrations, the production project's template must be pasted manually into the Supabase Dashboard (Authentication → Emails → Templates) — there's no working CLI link to the hosted project. The template's subject deliberately includes `{{ .Token }}` so repeat sign-in requests get distinct subjects instead of threading into one inbox conversation, hiding which link is still valid.

## Svelte/SvelteKit conventions used throughout

- Runes mode is forced project-wide via `svelte.config.js` (`compilerOptions.runes`), except inside `node_modules`.
- Mutating forms use `use:enhance` with `+page.server.ts` `actions`; a two-button toggle pattern (`{#each [...] as const as x}` + conditional Tailwind classes + a hidden input) is reused for every binary choice (White/Black, Player/Coach, etc.) instead of a native `<select>`.
- File inputs are visually hidden (`class="hidden"`) with a styled `<label for="...">` as the visible "Choose File" trigger — keep the original descriptive `<label>` text/for-association intact when doing this, since component tests assert on it via `getByLabelText`.
- Vitest environment is `node` by default; component tests that need the DOM opt in per-file with a `// @vitest-environment jsdom` pragma comment (not global config — see the note in `vite.config.ts`).

## Workflow notes

- **Log substantive requests as GitHub issues, and close them again on completion.** When the user's request is a real feature, bug, or task (not a trivial reply/confirmation/clarification), file it as a GitHub issue in `tomyka/mychess` via `gh issue create --title "..." --body "..."` — do this as part of handling the request, with a clean title/description reflecting the actual ask, not a raw prompt dump. Skip this for one-word replies, "yes"/"looks good" confirmations, or answers to Claude's own clarifying questions.
  - **Default (most issues):** a lightweight body — Problem, Proposed Solution, Acceptance Criteria, Non-Goals — borrowed from the `prd` skill's schema but skipping its discovery interview and the AI/Technical/Risk sections. No need to ask clarifying questions first; write it from context.
  - **Larger feature initiatives only** (new product surface, something that genuinely warrants stakeholder-style scoping): invoke the full `prd` skill — interview included — and either paste the resulting PRD into the issue body or link it, rather than using the lightweight template.
  - **Size the issue, and label it to match.** Every request gets classified, and the label must agree with the body's depth. The repo's own issue templates in `.github/ISSUE_TEMPLATE/` define the two sizes — mirror them when filing via `gh` (raw `--body` bypasses templates, so pass the label explicitly):
    - **Task** — self-contained, implementation-ready, no separate spec needed. Lightweight body per the bullet above. File with `--label size/small`, matching `small-task.yml`.
    - **Epic** — substantial feature or multi-part initiative that must go through brainstorm → spec → plan before any code. Body is the `prd` skill's output (or a link to it), and the issue is the backlog entry, *not* the spec. File with `--label size/large`, matching `feature-backlog.yml`. Link the child task issues from the epic body as a checklist so the breakdown is visible from one place.
    - When a request is genuinely ambiguous in size, prefer Epic and decompose — an epic that turns out small costs a label edit, whereas a task that turns out large silently skips the spec step.
  - **`auto-ok` — safe to work unattended (GitHub issue #189, epic #188).** A separate axis from size, because **size is not a proxy for safety**. An issue earns `auto-ok` only if *every* one of these holds:
    - **Its done-condition is checkable by a command** — `npm test`, `npm run check`, `npm run lint` — not by a human reading output and knowing what the numbers should be.
    - **It needs no product or UX decision.** Anything ambiguous is settled by the issue body, not by the agent's taste. An issue offering a choice of visual treatments ("a badge, dimmed styling, or a reason string") is not ready.
    - **It touches no production data**, and creates no account or fixture needing cleanup afterwards.
    - **It is not security-sensitive.**
    - **It is a task, not an epic**, and needs no brainstorming first.

    Only a human applies this label — an agent deciding for itself what is safe to do unattended defeats the point. Currently labelled: #185 (review a diff against a written plan), #186 (change two message values), #169 (internal perf refactor whose no-behaviour-change invariant is covered by `teaching.test.ts`).

    **#187 is the canonical counter-example** and is deliberately excluded: it is `size/small`, but its done-condition is read out of `debug:learn-plan` by someone who knows what the numbers should be, it exercises a destructive operation against a real repertoire for the first time, and it ends in a merge decision. Worth re-reading its thread before labelling anything that resembles it.

    `blocked` is its counterpart: an unattended run that stops applies it and comments what it needs.
  - **Closing:** once an issue's own Acceptance Criteria are actually met, close it (`gh issue close <n> --comment "..."`) — don't leave finished work sitting open. Pushing the code isn't sufficient by itself if the issue depends on a manual step outside Claude's control (a migration the user must run, a Supabase Dashboard setting, DNS/SMTP verification) — wait for that confirmation, or ask for it, before closing.
  - **QA/test accounts:** if verifying a task created a throwaway account in the database (e.g. testing a magic-link sign-in, a guest-conversion flow), remove it before treating the task as closed. The `SUPABASE_SERVICE_ROLE_KEY` in `mychess/.env` can delete it directly (see Database & migrations) — narrowly, only the specific account(s) created for that task's testing, never a broader cleanup sweep. Say what was deleted afterward rather than doing it silently.
- **Pushing to `main` depends on whether a human is watching (GitHub issue #190).** `main` auto-deploys to production via Vercel, so this rule is about who sees the result, not about trust:
  - **Supervised session** (a human is in the conversation): treat production as the test environment — commit and push directly to `main` without asking for confirmation first, since the project has no other users yet and a human sees the outcome immediately. This is the long-standing default and it stays.
  - **Unattended run** (no human present — see the `auto-ok` criteria above): **never push to `main` and never merge.** Work on a branch, then `gh pr create` linking the originating issue, and leave the PR for review. Shipping unreviewed code to a live site with nobody watching is the one thing autonomy must not be able to do, and CI (`ci.yml`) gates tests and lint on the PR.
  - Neither case extends to destructive git operations (force-push, history rewrites) — those still require asking, supervised or not.
- **When an unattended run can't proceed, blocking is the correct outcome (GitHub issue #191).** It is not a failure to be minimised or worked around — it is the right answer whenever the next step needs a decision or an access the run doesn't have. Before stopping, it must:
  1. **Comment on the issue** saying what it was doing, what blocked it, and *specifically* what a human has to supply — a secret, a decision between named options, a manual step. "Blocked on the database" is useless; "needs `SUPABASE_DB_URL` added to GitHub Actions secrets, see #156" is actionable.
  2. **Apply the `blocked` label**, so blocked issues are one filter away.
  3. **Push whatever partial work is genuinely useful** to a branch and name that branch in the comment, so the run's work isn't lost.
  4. **Stop.**

  The failure modes this exists to prevent, all of which look like progress:
  - Inventing a product or UX decision to keep moving. If the issue offers a choice and doesn't pick one, that is a block, not an invitation.
  - Skipping a migration and implementing against a schema that doesn't exist.
  - Disabling, skipping, or weakening a failing test to reach green.
  - Substituting a plausible-looking default for a value it was supposed to be given.

  A run that blocks correctly is working as intended. Epic #184's Task 6 is the worked example: it stopped dead on a migration needing a human, which was right — the only thing missing was somewhere to put that fact.
- When a request's scope is vague (no file/function named, no clear done-condition), ask one focused clarifying question before fanning out searches across the repo — don't burn tokens exploring to guess intent. Once scope is clear (named files, stated done-condition), act without further questions.
- Substantial features go through brainstorm → spec → plan → subagent-driven-development (spec-compliance review, then code-quality review, per task) in an isolated worktree; small iterative UI/UX fixes are made directly in-place, still gated on the full `vitest` + `svelte-check` run before commit. **Once a plan exists for a substantial feature, kick off subagent-driven-development automatically — don't ask for permission first.** The plan itself is the checkpoint; a user who wants to review before implementation starts says so when approving the plan, not by being asked again at this step.
- **After finishing a major feature, run a refactor pass before calling it done** (before `finishing-a-development-branch`, or before the final push if working in-place). Scope: the feature's own new files plus anything it touched or duplicates. Check for: logic copy-pasted instead of extracted (e.g. repeated auth/query boilerplate across `api/` routes), dead code left behind (old routes/exports superseded by the new feature but never deleted), drift from documented conventions (pure-logic-in-`lib/` vs I/O-in-`lib/server/` split, existing shared helpers reinvented locally), and files that grew unwieldy. Fix what's cheap inline; file a GitHub issue for anything bigger. This is additive to the existing spec-compliance/code-quality review step, not a replacement for it.
