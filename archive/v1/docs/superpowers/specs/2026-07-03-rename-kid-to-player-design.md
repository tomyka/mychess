# Rename "Kid" → "Player" (code + DB schema) — Design Spec

**Date:** 2026-07-03
**Status:** Approved for planning
**Scope:** Full rename of every "kid" reference to "player" — code identifiers, route paths, UI text, the `role` value, and the physical database schema (tables, columns, foreign keys, indexes, constraints, policies, functions). Nothing named "kid" remains.

## Problem / Goal

The platform models trainees as "kid" throughout (route group `(kid)`, `kid_id` columns, `kid_stats` table, `role = 'kid'`, RPC `sync_kid_stats`, UI text). The product term is **Player**. Rename everything so code and schema match the domain language. This precedes the broader platform rework (public-first landing, auth, roles), so later work is written against the new names.

## Approach: rewrite migrations + reset (pre-production)

The platform is **not in production** — no data must be preserved — so instead of layering an in-place rename migration on top, we **rewrite the canonical migration files** so the schema is *born* player-native, then **reset the dev database** and re-run all migrations from scratch. Foreign-key, index, unique, and primary-key constraint names are auto-generated by Postgres from table/column names, so a reset produces clean `*_player_*` names for free — no fragile catalog-hunting rename SQL.

## Non-goals

- No behavioural changes — pure rename. Same queries, same auth, same UI flows.
- Not renaming the `coach` role, `coach_id`, or coach-owned columns.

## Database — rewrite these migration files in place

Only four migrations contain "kid": **`0001_core_tables.sql`** (13), **`0002_rls.sql`** (34), **`0003_rpcs.sql`** (20), **`0005_phase_b.sql`** (38). Edit each so it reads player-native:

### `0001_core_tables.sql`
- Table `kid_stats` → `player_stats`.
- Column `kid_id` → `player_id` in: `repertoires`, `reviews`, `sessions`, `player_stats` (PK), `badges_earned` (PK part), `coach_notes`, `equipped_cosmetics` (PK).
- `profiles.role` check: `check (role in ('kid','coach'))` → `check (role in ('player','coach'))`.
- Inline `unique (kid_id, move_id)` etc. → `player_id`.

### `0002_rls.sql`
- Every `kid_id = auth.uid()` and `… where k.id = kid_id …` expression → `player_id`.
- Policy names: `repertoires_kid_all`→`repertoires_player_all`, `moves_kid_all`→`moves_player_all`, `reviews_kid_all`→`reviews_player_all`, `sessions_kid_all`→`sessions_player_all`, `review_events_kid_all`→`review_events_player_all`, `kid_stats_self`→`player_stats_self`, `kid_stats_self_insert`→`player_stats_self_insert`, `kid_stats_coach`→`player_stats_coach`, `badges_kid_read`→`badges_player_read`, `coach_notes_kid_read`→`coach_notes_player_read`, `cosmetics_kid_all`→`cosmetics_player_all`, `cosmetics_kid_insert`→`cosmetics_player_insert`. Table references `on public.kid_stats` → `on public.player_stats`.

### `0003_rpcs.sql`
Rewrite function signatures + bodies:
- `update_xp_and_level(p_kid_id …)` → `update_xp_and_level(p_player_id …)` (keep name).
- `update_streak(p_kid_id)` → `update_streak(p_player_id)` (keep name).
- `submit_session_result(…)` — body references to `sessions.kid_id`, `kid_stats`, locals `v_kid_id` → `player_id`, `player_stats`, `v_player_id`.
- All `p_kid_id`/`v_kid_id` params & locals → `p_player_id`/`v_player_id`.

### `0005_phase_b.sql`
- Tables `quests`, `weekly_leaderboard` (PK), `assigned_repertoires`: `kid_id` → `player_id` (incl. `unique(kid_id, …)`).
- Policies `"Kids manage own quests"`→`"Players manage own quests"`, `"Kids see own assignments"`→`"Players see own assignments"`, and their `kid_id = auth.uid()` expressions → `player_id`.
- Functions: `sync_kid_stats(p_kid_id)` → **`sync_player_stats(p_player_id)`** (name + body; body uses `player_stats(player_id, …)`, `on conflict (player_id)`); `increment_new_cards(p_kid_id …)` and `update_weekly_leaderboard(p_kid_id …)` → `p_player_id` params + `player_stats`/`weekly_leaderboard.player_id` bodies.

Other migrations (`0004` seed, `0006`–`0016`) contain no "kid" and are unchanged.

## Code changes

Mechanical, repo-wide (~30 files, ~144 occurrences). Transformation rules:

- **Route group:** `src/routes/(kid)/` → `src/routes/(player)/` (route groups don't change URLs; `$types` regenerate).
- **Coach sub-routes:** `src/routes/(coach)/coach/kids/` → `.../coach/players/`; `[kid_id]/` → `[player_id]/`; update `params.kid_id` → `params.player_id` and any `/coach/kids/...` hrefs → `/coach/players/...`.
- **Tables:** `.from('kid_stats')` → `.from('player_stats')`.
- **Columns:** `.eq('kid_id', …)`, `kid_id:` keys, `.select('… kid_id …')` → `player_id`.
- **RPC calls:** `.rpc('sync_kid_stats', …)` → `.rpc('sync_player_stats', …)`; every `.rpc(…, { p_kid_id: … })` arg key → `p_player_id` (named args — see Risks).
- **Role literals:** `role !== 'kid'` / `role === 'kid'` / `role: 'kid'` → `'player'` (e.g. `(player)/+layout.server.ts` guard, `hooks.server.ts` guest-profile insert, `welcome` role option `id: 'kid'` → `'player'`).
- **Identifiers:** `kidId`, `kidIds`, `kid_name`, `kidName`, client-side `p_kid_id`, etc. → player equivalents.
- **Component/prop names & comments & UI text:** any `kid`/`Kids` → `player`/`Players`.

The `(coach)` group, `role = 'coach'`, and `coach_id` are untouched.

## Operational steps (after code + migrations are merged)

1. Reset the dev database so the rewritten migrations run from scratch: `supabase db reset` (drops & re-applies all migrations). If the CLI isn't linked for a remote reset, run the migrations against a fresh DB via the SQL editor / `supabase db push` on a clean schema.
2. Re-run the FIDE import (GitHub Action *FIDE monthly import*, or `npm run fide:import`) to repopulate `fide_players` (~8k rows, ~1 min).
3. Re-create your own profile via the normal welcome flow.

Because everything is torn down and rebuilt, there is no partial-state / breakage window to coordinate.

## Testing

- `npm test` (vitest) fully green — most tests are pure logic; the rename only touches identifier-named vars/fixtures, no assertions of behaviour.
- `npm run check` — no new type errors beyond the known pre-existing set.
- Post-reset manual smoke: player dashboard loads (stats/quests/leaderboard); a drill/review submits (exercises `submit_session_result`, `sync_player_stats`, `update_weekly_leaderboard`); coach view of a player (`/coach/players/[player_id]`) loads.

## Risks

- **RPC named-arg keys** — the easiest thing to miss; a stale `{ p_kid_id }` key silently passes `undefined`. The plan greps every `.rpc(` call and updates arg keys alongside the param rename.
- **Function bodies** — a missed `kid_id`/`kid_stats` inside a rewritten body fails only at call time (not covered by unit tests) → the manual smoke of a drill submission covers the write-path RPCs.
- **Reset destroys dev data** — `fide_players` and the current profile are wiped by design; re-import + re-register restore them. No production data exists.
- **Grep completeness** — the plan verifies zero `kid` remains via `grep -ri kid src/ supabase/` returning nothing (case-insensitive) as the definition of done.
